# Benchmarks 💖

Generated by `wly bench`. Do not edit by hand.

**No sweep has run yet.** This file is a placeholder so the first real run shows up
as a reviewable diff instead of a brand new file. `wly bench` rewrites it whole, which is
why the method lives in `jvm-profiles.toml` and `CLAUDE.md` rather than here.

The candidate matrix is 25 enabled profiles in `jvm-profiles.toml`: Temurin 21
and 25 crossed with G1, Parallel, Serial, ZGC and generational Shenandoah,
GraalVM 21 and 25 crossed with the collectors Graal supports, and a heap sweep at

they need an image that does not exist yet.

To fill it in:

```bash
ssh -i ~/.ssh/oracle-weloveyou ubuntu@100.103.121.9 '/opt/deploy/bench-power.sh start'

# pass 1 - screen throughput across the whole matrix, cheaply
gh workflow run bench -f workload=worldgen -f runs=1 -f radius=400 \
  -f out=BENCHMARKS-screening.md -f shards='["1/3","2/3","3/3"]'

# pass 2 - confirm the winners at full depth. --only takes a list
gh workflow run bench -f workload=worldgen -f runs=3 -f radius=1000 \
  -f only=j25-g1-coh,baseline-j21

# pass 3 - the tick load, on the profiles that survived pass 2
gh workflow run bench -f workload=players -f runs=3 \
  -f only=j25-g1-coh,baseline-j21 -f shards='["1/3","2/3","3/3"]'
```

Pass 3 is the one that can see a tick-bound regression. Passes 1 and 2
pregenerate chunks, which barely ticks entities, so TPS reads 20 on every profile
no matter what the flags do. Calibrate it first: run one profile with
`-f workload=players -f runs=1` and raise `-f load=` until MSPT p95 clears the
idle floor, because a load that cannot move p95 measures nothing and still prints
a plausible row.

The sweep powers the box off when it finishes, always, including on failure.

Four things to know before reading any number that lands here:

- **A screening row and a confirmed row are not comparable.** A single run has no
  variance to report; that is the entire reason the second pass exists.
- **The pack grows.** These measure `pack/stable` as it is today, Terralith,
  Oritech and performance mods, with gameplay mods still to come. The report
  prints the mod count it measured against for exactly this reason. A row taken
  against 17 pack entries says little about one taken against 60.
- **Throughput rows and tick rows read in opposite directions.** Workloads A and
  B are read by chunks/s, higher being better; C, D and E by MSPT p95, lower
  being better. `vs base` is signed to match, so a positive number means "better"
  in every table, and the chunks/s column is blank on a tick workload rather than
  showing a zero that looks like a measurement.
- **Rows taken at different `--load` are not comparable**, the same way rows
  taken against different pack sizes are not.
