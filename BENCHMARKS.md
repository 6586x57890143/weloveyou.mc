# Benchmarks

Generated by `wly bench`. Do not edit by hand.

**No sweep has run yet.** This file is a placeholder so the first run produces a
reviewable diff rather than a new file. `wly bench` rewrites it whole, which is
why the method lives in `jvm-profiles.toml` and `CLAUDE.md` rather than here.

The candidate matrix is 18 enabled profiles in `jvm-profiles.toml`: Temurin 21
and 25 crossed with G1, Parallel, Serial, ZGC and generational Shenandoah, and
GraalVM 21 and 25 crossed with the collectors Graal supports. Four more are
declared and disabled because they need an image that does not exist yet.

To fill it in:

```bash
ssh -i ~/.ssh/oracle-weloveyou ubuntu@100.103.121.9 '/opt/deploy/bench-power.sh start'

# pass 1 - screen the whole matrix cheaply
gh workflow run bench -f workload=both -f runs=1 -f radius=500 \
  -f out=BENCHMARKS-screening.md

# pass 2 - confirm the top few at full depth, one profile per run
gh workflow run bench -f workload=both -f runs=3 -f radius=1000 \
  -f only=j25-g1-coh
```

The sweep powers the box off when it finishes, always, including on failure.

Two things to know before reading any number that lands here:

- **A screening row and a confirmed row are not comparable.** A single run has no
  variance to report; that is the entire reason the second pass exists.
- **The pack grows.** These measure `pack/stable` as it is today — Terralith,
  Oritech and performance mods, with gameplay mods still to come. The report
  prints the mod count it measured against for exactly this reason. A row taken
  against 17 pack entries says little about one taken against 60.

The first question this exists to answer: does `-XX:+UseCompactObjectHeaders`
help a modded Minecraft server? It ships **on** in production today because JEP
519 went production in JDK 25 and Minecraft is the archetypal small-object
workload — not because anyone has measured it here.
